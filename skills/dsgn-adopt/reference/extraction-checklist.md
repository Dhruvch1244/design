# Extraction checklist

Step-by-step for `dsgn-adopt`. Work through these in order — later steps
depend on what earlier ones find.

## Step 0 — check for an existing source of truth

```
CLAUDE.md, AGENTS.md, .claude/skills/*/SKILL.md, DESIGN.md, CONVENTIONS.md,
STYLEGUIDE.md, docs/design*.md
```

If any of these already document real conventions, **stop** — read and
defer to it instead of extracting. If one exists but is clearly stale
(references a library no longer in `package.json`, say), note the drift
explicitly in your output rather than silently overriding it.

## Step 1 — identify the real stack

Read the actual dependency manifest — don't infer from a README or an
external doc. Look for:

- **Framework** + version (Next.js? Remix? plain Vite+React? Angular?
  Vue/Nuxt? SvelteKit?) — and whether it's pinned behind or ahead of what
  your training data assumes is current (check the actual installed
  version against what you know, the same instinct `philosophy/AGENTS.md`'s
  pillar #6 describes).
- **UI primitive library**, if any: `@radix-ui/*`, `@base-ui/*` (formerly
  Base UI), `@headlessui/*`, MUI (`@mui/material`), Chakra
  (`@chakra-ui/react`), Ant Design (`antd`), Mantine, react-aria, or none
  (hand-rolled). Grep `package.json` — don't guess from how the UI *looks*,
  since visually similar components can be built on completely different
  primitives.
- **Component CLI/registry tooling**, if any: a `components.json` file
  means shadcn's CLI (or a shadcn-compatible fork) was used to install
  components — check its `style`, `baseColor`, and `aliases` fields, they
  tell you the actual installed convention without reading a single
  component file yet.
- **Styling approach**: Tailwind (`tailwind.config.*` or a `@tailwindcss/*`
  postcss plugin for v4), CSS Modules (`*.module.css` files), CSS-in-JS
  (`styled-components`, `@emotion/*`, `vanilla-extract`), or plain
  `.css`/`.scss`.
- **Variant/class utility**: `class-variance-authority` (cva),
  `tailwind-variants`, `clsx`/`classnames` alone, or none.

## Step 2 — read real component files

List the component directory (common locations: `components/`,
`src/components/`, `app/components/`, `ui/`, `src/components/ui/`), then
**actually read**, not just list, at least 3-5 of the most fundamental
ones — whatever plays the role of Button, Card, Input here. For each, note:

- The **real variant names** (e.g. `default`/`outline`/`ghost`, not a
  guessed shadcn-typical set — this codebase's actual list, which may
  differ from what's typical).
- The **real size names**, if sizes exist as a variant axis.
- Any **data-\* attribute convention** (e.g. `data-slot="button"` — newer
  shadcn generations use this; older ones don't).
- Whether variants are exhaustive CVA definitions or ad-hoc conditional
  classNames.
- The **import path convention** (`@/components/ui/button`,
  relative imports, a package alias).

## Step 3 — find (or rule out) a design-token source

Look for a CSS custom-property block (`:root { --... }`), a `theme.ts`/
`theme.js`/`theme.json`, or a `tailwind.config` `theme.extend` block. If
found, extract the real palette/radius/spacing scale. If genuinely absent
(colors/spacing are hardcoded ad-hoc per component), **write that down as
the finding** — don't invent a token system that isn't there and describe
it as if it were the convention.

## Step 4 — accessibility patterns already present

Grep for `aria-`, `role=`, and semantic-element usage in the same sample of
files read in Step 2. Note real examples found (or their absence) — don't
assume a baseline level of a11y maturity either way.

## Step 5 — write the output

Target path: `.claude/skills/<repo-name>-conventions/SKILL.md` in the
**target repo** (create the directory if it doesn't exist). Use this shape:

```markdown
---
name: <repo-name>-conventions
description: Real, extracted UI conventions for <repo-name> — <one-line summary of stack + styling approach>. Generated by dsgn-adopt; re-run if the stack changes materially.
---

# <repo-name> — extracted conventions

Extracted <date> from the repo's own code, not invented. Every claim below
cites the real file it came from.

## Stack

- Framework: <name + version>, from `package.json`
- UI primitives: <library, or "none — hand-rolled">
- Styling: <approach>
- Variant utility: <cva / tailwind-variants / none>

## Real components found

| Component | File | Variants | Notes |
|---|---|---|---|
| Button | `src/components/ui/button.tsx` | default, outline, secondary, ghost, destructive, link | `data-slot="button"`, sizes include icon-xs/icon-sm/icon-lg |

(one row per component actually read in Step 2 — not the full directory
listing, only the ones you opened and verified)

## Design tokens

<extracted palette/radius/spacing, OR "No consistent token source found —
colors/spacing are set ad-hoc per component; see `<file>` and `<file>` for
two different approaches to the same problem.">

## Accessibility patterns observed

<real examples found, with file references, or "No consistent pattern
observed in the files read — verify explicitly rather than assuming
coverage.">

## Applying this

New UI in this repo should match the real variant/prop vocabulary above,
not a generic shadcn/Radix/MUI default — e.g. use this repo's own
`variant="secondary"` semantics, not a different library's idea of what
"secondary" means.
```

Keep the table to components actually read, not a full directory dump —
padding it with unread files reintroduces exactly the "invented, not
observed" problem this whole skill exists to avoid.
